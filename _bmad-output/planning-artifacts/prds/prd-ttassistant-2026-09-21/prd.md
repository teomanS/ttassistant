# PRD: ttassistant (Terraform Assistant CLI)
*Enterprise Architectural Co-Pilot for Azure Terraform Monorepos*

---

## 0. Document Purpose

This Product Requirements Document (PRD) defines the functional requirements, architectural boundaries, and user journeys for **`ttassistant`**, an enterprise-grade, terminal-native conversational CLI assistant. It serves as the single source of truth for platform engineers, infrastructure developers, and downstream architectural and implementation workflows. 

`ttassistant` builds directly upon the foundational discoveries in `_bmad-output/planning-artifacts/briefs/brief-ttassistant-2026-09-20/brief.md` and `addendum.md`. All domain terms are anchored in §3 Glossary. Every functional requirement (FR) is assigned a globally unique, immutable identifier (FR-1 through FR-16) to ensure strict traceability across downstream implementation epics, test suites, and code reviews.

---

## 1. Vision

Modern enterprise cloud infrastructure repositories often suffer from repository fragmentation, copy-paste anti-patterns, and severe pull-request review bottlenecks. In multi-subscription Azure monorepos, application engineers spend days navigating opaque folder hierarchies (`<resource-type>/<subscription>`), frequently hardcoding environment strings and inadvertently omitting mandatory enterprise security controls—most notably Private Endpoints and Private DNS Zone integrations. Consequently, platform and security teams spend hours performing manual code reviews and cleaning up non-compliant pull requests.

**`ttassistant`** eliminates this friction by shifting enterprise architecture and security compliance left directly into the developer's terminal. Executed within the developer's VSCode terminal (on both Windows and Linux) without requiring local `terraform` or `az` binary dependencies, `ttassistant` conducts an interactive guided dialogue with the engineer. It deterministically analyzes repository topology, resolves cross-resource dependencies (such as Virtual Networks, Subnets, and Resource Groups) into decoupled `data "azurerm_*"` blocks, and dynamically enforces corporate Markdown specifications (`common_standards/*.md`) for naming, tagging, and remote state backend mapping.

By automating the complete enterprise security triad—denying public network access, provisioning private endpoints, and linking private DNS zones—for any Azure PaaS resource, while supporting all Azure resource types through a tiered catalog architecture, `ttassistant` reduces platform review times from one hour to under fifteen minutes, prevents production security vulnerabilities, and accelerates compliant developer onboarding.

- **Autonomous CI/CD Pipeline Operators (Zero Auto-Apply):** Engineers seeking a tool that automatically runs `terraform apply`, modifies remote state in-flight, or orchestrates deployments without human review. `ttassistant` is strictly an authoring and refactoring co-pilot.

### 2.3 Key User Journeys

#### UJ-1. Elena Scaffolds a Fully-Isolated Azure SQL Database in Payments-Prod
- **Persona & Context:** Elena, Senior Backend Engineer, needs to add a production Azure SQL Database to the `payments-prod` subscription. She does not know the exact VNet topology or the company naming convention for SQL servers.
- **Entry State:** Elena opens her VSCode terminal in the root of the local Bitbucket repository on her Linux workstation. Neither `terraform` nor `az` CLI is installed locally.
- **Path:**
  1. Elena runs `ttassistant` in her terminal.
  2. The CLI initiates an interactive guided dialogue, prompting Elena to select or input her target Azure subscription (`payments-prod`) and target resource type (`azurerm_mssql_server` / SQL Database).
  3. `ttassistant` parses `common_standards/*.md`, identifying the required naming schema (`sql-payments-prod-###`), mandatory cost-center tags, and the designated Azure Blob state backend for `payments-prod`.
  4. `ttassistant` scans the repository's existing networking folders, identifies two candidate subnets configured for private endpoints, and prompts Elena: *"Select target subnet for Private Endpoint: [1] snet-pep-backend (Recommended), [2] snet-pep-data"*. Elena selects `[1]`.
  5. `ttassistant` constructs the decoupled HCL blocks: `azurerm_mssql_server` (with public network access disabled), `data "azurerm_resource_group"`, `data "azurerm_subnet"`, `azurerm_private_endpoint`, and the `private_dns_zone_group` linked to the Hub Private DNS zone.
  6. `ttassistant` presents an in-terminal summary and unified diff for `azurerm_mssql_server/payments-prod/main.tf` and `backend.tf`.
  7. Elena enters a quick conversational tweak: *"Set minimum TLS version to 1.2"*. The CLI immediately refreshes the diff with `minimum_tls_version = "1.2"`.
- **Climax:** Elena reviews the updated diff, confirms with `Y`, and `ttassistant` writes the compliant files directly to disk.
- **Resolution:** Elena stages and commits the files to Git; the PR passes CI linting and platform approval on the first pass.
- **Edge Case:** If `payments-prod` does not contain an existing subnet definition, `ttassistant` alerts Elena, identifies candidate subnets in shared network directories, or offers to scaffold the missing network dependency before proceeding.

#### UJ-2. Tariq Updates Corporate Tagging and Naming Standards in Git
- **Persona & Context:** Tariq, Platform Engineering Lead, needs to roll out a new mandatory tag (`data-classification`) and update the naming prefix for Azure Storage Accounts across 40 subscriptions.
- **Entry State:** Tariq opens the repository on his Windows laptop.
- **Path:**
  1. Tariq opens `common_standards/naming_conventions.md` and `common_standards/tagging_baseline.md`.
  2. He updates the rules in pure Markdown and commits the change to the `main` branch.
  3. All developers pulling the latest Git changes immediately execute `ttassistant`.
- **Climax:** The CLI dynamically reads the modified Markdown files on startup, immediately enforcing the new tagging baseline and naming conventions across all future authoring sessions.
- **Resolution:** No CLI source code changes, recompilations, or binary updates were required to distribute the new organizational policy.

## 3. Glossary

The following domain nouns are strictly defined for this product. Downstream technical specifications, user documentation, and code must use these terms verbatim without introducing synonyms:

- **`ttassistant`**: The terminal-native interactive CLI tool executed by engineers at the repository root.
- **`common_standards/`**: The designated top-level repository directory containing human-readable and machine-parsed Markdown (`.md`) specification files that dictate corporate infrastructure rules.
- **Markdown Gold Standards**: The declarative architectural rules, naming conventions, tagging baselines, state backend mappings, and subnet placement heuristics stored within `common_standards/*.md`.
- **Repository Topology**: The file and directory hierarchy of the monorepo, following `<resource-type>/<subscription>/` partitions and non-uniform legacy resource placements.
- **Decoupled Data Source**: A Terraform `data "azurerm_*"` block dynamically referencing an external or upstream resource (e.g. Resource Group, Virtual Network, Subnet) by name or tag query, avoiding hardcoded resource IDs and fragile `terraform_remote_state` dependencies.
- **Enterprise Security Triad**: The mandatory triad of security controls generated for Azure PaaS resources: (1) public network access denied, (2) `azurerm_private_endpoint` bound to an internal subnet, and (3) `private_dns_zone_group` mapped to centralized Hub Private DNS zones.
- **Governed Agency**: The operating principle ensuring `ttassistant` operates strictly as a human-confirmed co-pilot; silent file modifications are prohibited, terminal diffs are mandatory for existing code, and execution of `terraform apply` is out of scope.
- **Zero Local Binaries**: The architectural capability of `ttassistant` to parse, scaffold, format, and emit valid Terraform HCL without invoking or requiring local installations of `terraform`, `terragrunt`, or the Azure CLI (`az`).

## 4. Features

### 4.1 Feature 1: Interactive Guided Dialogue & Cross-Platform CLI Interface

**Description:** Provides an interactive, terminal-based conversational interface running inside the VSCode integrated terminal on Windows (PowerShell, CMD) and Linux (Bash, Zsh). It guides developers through provisioning any Azure resource via progressive disclosure prompts. The CLI operates with zero external binary dependencies—it does not require `terraform` or `az` CLI to be installed on the host system. Realizes UJ-1. `[ASSUMPTION: §4.1: Developers have access to Python 3.10+ in their VSCode development environment to run the tool from the internal repository.]`

#### Functional Requirements:

##### FR-1: Cross-Platform Terminal Runtime
The CLI must execute interactively inside the VSCode integrated terminal across Linux (x86_64, arm64) and Windows (PowerShell, Command Prompt, WSL) environments without platform-specific rendering artifacts.
- **Consequences (testable):**
  - CLI binary launches and renders interactive ANSI/VT100 prompt components cleanly on Windows Terminal and Linux Bash without escape code corruption.
  - Keyboard navigation (arrows, enter, tab-completion, escape) functions identically across platforms.

##### FR-2: Guided Interactive Dialogue Flow
The CLI must prompt the user step-by-step for core provisioning parameters: target subscription, target Azure resource type, workload name, and service-specific configurations.
- **Consequences (testable):**
  - Entering invalid input (e.g., characters forbidden in Azure resource names) triggers immediate inline validation and re-prompts the user without crashing the session.
  - Users can cancel, step back, or input conversational tweaks at any point before final staging.

##### FR-3: Zero Local Binaries Architecture
The CLI must perform all repository scanning, Markdown parsing, HCL generation, and validation internally without invoking `terraform`, `az`, or external shell binaries.
- **Consequences (testable):**
  - Scaffolding completes successfully in a sanitized container environment where `PATH` contains neither `terraform` nor `az`.
  - Emitted `.tf` files conform to standard Terraform HCL2 syntax and formatting conventions directly from memory.
- **Out of Scope:** Local execution of `terraform init`, `terraform plan`, or `terraform apply`.

---

### 4.2 Feature 2: Repository Topology Discovery & Subnet Dependency Archaeology

**Description:** Analyzes the local repository structure to understand resource distribution and discover shared dependencies. Handles non-uniform folder structures (`<resource-type>/<subscription>/`), parses existing Terraform files to discover existing Resource Groups and Subnets, and generates decoupled `data "azurerm_*"` blocks instead of hardcoded strings. Realizes UJ-1.

#### Functional Requirements:

##### FR-4: Monorepo Topology Traversal
The CLI must recursively scan the repository starting from the working directory root to map all existing `<resource-type>/<subscription>/` directories and resource locations.
- **Consequences (testable):**
  - Successfully identifies target subscription folders even when folder naming conventions vary across resource types (e.g., `resource-groups/sub-prod/` vs `rg/sub_prod/`).

##### FR-5: Subnet & Resource Group Discovery
The CLI must analyze existing `.tf` files across networking and foundation folders to discover available Subnets, Virtual Networks, and Resource Groups within the target subscription.
- **Consequences (testable):**
  - Identifies existing subnets designated for Private Endpoints by inspecting subnet configurations and tags in the repository.
  - Automatically identifies the parent Resource Group for the target subscription.

##### FR-6: Collaborative Subnet Selection & Missing Dependency Scaffolding
When multiple candidate subnets exist for a resource's private endpoint, the CLI must present an interactive selection prompt displaying candidate subnet names, CIDRs, and purpose recommendations. If dependencies are missing, it offers proactive scaffolding.
- **Consequences (testable):**
  - If a subnet matching `common_standards/` recommendations exists, the CLI marks it as `(Recommended)` and sets it as the default choice.
  - If multiple candidate subnets match equally without specific recommendation, the CLI presents an interactive numbered menu sorted by repository proximity.
  - If no candidate subnet exists within the subscription, the CLI prompts the user with the option to scaffold the missing subnet/VNet definition in its designated networking folder or wire a cross-subscription shared network lookup.

##### FR-7: Decoupled Data Source Scaffolding
The CLI must emit Terraform `data "azurerm_*"` blocks for all discovered upstream dependencies (Resource Groups, Subnets, VNets) rather than hardcoded resource IDs or `terraform_remote_state` blocks.
- **Consequences (testable):**
  - Generated code contains zero `terraform_remote_state` data blocks.
  - Resource references use `data.azurerm_resource_group.<name>.name` and `data.azurerm_subnet.<name>.id`.

---

### 4.3 Feature 3: Dynamic Markdown Standards Engine (`common_standards/`)

**Description:** Dynamically ingests and parses specification files located in the `common_standards/` directory. Translates human-readable Markdown policies into deterministic constraints for naming conventions, mandatory tags, backend state storage mappings, and architectural heuristics. Allows platform teams to distribute policy updates via Git without CLI re-releases. Realizes UJ-2. `[ASSUMPTION: §4.3: Platform engineers will commit common_standards/*.md directly to the repository root so it is present in every developer clone.]`

#### Functional Requirements:

##### FR-8: Dynamic Markdown Specification Ingestion & Fail-Fast Policy
The CLI must discover and parse all `.md` files within `common_standards/` at the start of every session, supporting Markdown tables, key-value lists, and optional YAML frontmatter.
- **Consequences (testable):**
  - Modifying a naming convention or adding a mandatory tag in `common_standards/*.md` immediately alters the validation and output of the next CLI invocation without recompiling the binary.
  - If `common_standards/` is missing or empty, the CLI terminates immediately (exit code 1) with an actionable error message instructing the engineer to pull the corporate standards.

##### FR-9: Automated Naming & Tagging Rule Enforcement
The CLI must enforce the naming conventions and mandatory tag baseline defined in `common_standards/*.md` for every generated resource.
- **Consequences (testable):**
  - Resource names are automatically formatted to match required prefixes, suffixes, and Azure length/character constraints.
  - Mandatory tags (e.g., `environment`, `owner`, `cost-center`, `data-classification`) are automatically populated into the `tags = { ... }` block.

##### FR-10: Automated Azure Blob Backend Mapping
The CLI must dynamically resolve the Azure Storage Account, Resource Group, Container, and state key for the target subscription from `common_standards/*.md` (or existing subscription patterns) and scaffold the `terraform { backend "azurerm" { ... } }` configuration.
- **Consequences (testable):**
  - Scaffolding a new resource in `<resource-type>/<subscription>` creates a `backend.tf` file with the exact storage account, container, and unique key path required for that subscription.
  - State keys are isolated per subscription and resource type, preventing state collision.

### 4.4 Feature 4: Tiered Azure Resource Support & Enterprise Security Triad Bundler

**Description:** Supports all Microsoft Azure resources from day one through a two-tiered catalog architecture. Tier 1 provides deep, guided conversational prompts and mandatory Enterprise Security Triad bundling for all PaaS and foundational services; Tier 2 provides universal syntax generation for all long-tail AzureRM provider resources. Realizes UJ-1. `[ASSUMPTION: §4.4: The enterprise uses a centralized Hub-and-Spoke networking model where Private DNS Zones are centrally hosted and referenced across subscriptions.]`

#### Functional Requirements:

##### FR-11: Tiered Azure Resource Catalog Architecture
The CLI must support code generation for all Azure resources supported by the `azurerm` Terraform provider using a two-tier delivery model:
- **Tier 1 (Guided Enterprise PaaS & Foundation):** Full guided conversational prompts, automated private endpoint and DNS zone group bundling, subnet discovery, and specialized attribute validation for core enterprise services (Storage Accounts, Key Vaults, Azure SQL, Cosmos DB, Event Hubs, PostgreSQL, MySQL, Redis, App Services, VNets, Subnets, Resource Groups).
- **Tier 2 (Universal Azure Long-Tail):** Universal syntax scaffolding for all other `azurerm_*` resources supported by the provider, generating syntactically valid HCL blocks with mandatory `common_standards/` tags, naming prefixes, decoupled data sources, and subscription backend wiring.
- **Consequences (testable):**
  - Selecting any Tier 1 resource initiates the specialized guided dialogue with security bundling.
  - Selecting any arbitrary valid AzureRM resource outside Tier 1 successfully emits compliant HCL blocks with standard enterprise tags, backend state, and provider configuration.

##### FR-12: Mandatory Public Network Denial
For all Azure PaaS resources supporting public network restrictions (e.g. Storage Accounts, Key Vaults, Azure SQL, Cosmos DB, Event Hubs, Redis), the CLI must explicitly set public access denial arguments in the primary resource block.
- **Consequences (testable):**
  - Generated PaaS resources include `public_network_access_enabled = false` (or resource-equivalent parameter) by default.
  - The CLI alerts the user if an explicit request to enable public access contradicts `common_standards/` security policy.

##### FR-13: Automated Private Endpoint & DNS Zone Group Bundling
For any PaaS resource provisioned, the CLI must automatically scaffold the accompanying `azurerm_private_endpoint` resource and wire its `private_dns_zone_group` to the corporate Hub Private DNS Zone.
- **Consequences (testable):**
  - Generated code includes an `azurerm_private_endpoint` block referencing the selected subnet ID and the target resource ID.
  - Includes a `private_dns_zone_group` block with the designated corporate Private DNS zone ID (resolved via `common_standards/` or data source).
- **Out of Scope:** Creation of new Hub Private DNS Zones inside workload spoke subscriptions (Hub DNS is managed centrally).

### 4.5 Feature 5: Governed Agency Direct-to-Disk Authoring & Diff Review

**Description:** Stages and writes generated Terraform files directly to the appropriate `<resource-type>/<subscription>/` directory on disk. When modifying or augmenting an existing directory, the CLI operates in inspection and remediation mode, presenting an interactive unified diff in the terminal and enabling in-session conversational refinements before explicit confirmation. Realizes UJ-1.

#### Functional Requirements:

##### FR-14: Target Directory Scaffolding & Existing Folder Remediation
The CLI must calculate destination paths (`<resource-type>/<subscription>/`) and support both greenfield creation and existing folder augmentation.
- **Consequences (testable):**
  - For new workloads, files are written to the exact expected directory (`main.tf`, `variables.tf`, `outputs.tf`, `backend.tf`, `data.tf`).
  - When executed targeting an existing folder, the CLI inspects the existing files for missing mandatory tags, public network access exposures, or missing Private Endpoints, and stages corrective additions as a proposed diff.

##### FR-15: Unified In-Terminal Diff Display
Before writing new files or modifying existing configurations, the CLI must render a unified terminal diff showing added lines (`+`), removed lines (`-`), and unchanged context.
- **Consequences (testable):**
  - Diff output uses standard color coding (green for additions, red for deletions) compatible with VSCode terminal color themes.
  - The diff accurately reflects the exact bytes that will be written to disk.

##### FR-16: In-Session Conversational Refinement & Human Confirmation Gate
Before committing writes to disk, the CLI must provide an interactive confirmation gate that allows the engineer to accept `[Y]`, cancel `[N]`, or supply conversational tweak instructions to re-generate the diff.
- **Consequences (testable):**
  - Entering conversational tweak instructions (e.g., *"Change replication to GRS"* or *"Add tag team=core"*) updates the staged HCL in memory and immediately re-renders the terminal diff.
  - Pressing `N`, `Escape`, or `Ctrl+C` exits the session without modifying, creating, or corrupting any files in the workspace.
  - Under no circumstances does the CLI invoke `terraform apply` or execute automated infrastructure deployments.

## 5. Non-Goals (Explicit)

The following capabilities are explicitly outside the scope of `ttassistant` v1:

- **Strictly Zero Auto-Apply:** `ttassistant` will never execute `terraform apply`, `terraform destroy`, or make mutations against live cloud infrastructure. Deployment execution is reserved exclusively for CI/CD pipelines.
- **No Remote State Surgery:** Automated migration of remote state or cross-state surgery (e.g. executing `terraform state mv` or manipulating remote state JSON) is out of scope.
- **No Direct Cloud Authentication / Cloud API Calls:** The CLI does not authenticate to Microsoft Azure or execute Azure Resource Manager (ARM) REST APIs. All discovery is performed locally against the Git repository. `[ASSUMPTION: §8.2: Zero cloud API calls means ttassistant relies entirely on static file analysis of the Git repository rather than live Azure Resource Graph queries.]`
- **No Multi-Cloud Support:** AWS, GCP, and other cloud providers are strictly excluded; v1 is 100% Azure-dedicated.
- **No Autonomous File Mutations:** The CLI will never silently overwrite or modify files without explicit terminal diff display and interactive user confirmation.
- **No Visual / GUI Canvas:** Diagram-to-code visual canvases are out of scope; `ttassistant` is purely terminal-native.

## 6. MVP Scope

### 6.1 In Scope
- Interactive guided dialogue CLI running inside VSCode terminal on Linux and Windows.
- Packaging and distribution via the enterprise internal Python repository.
- Tiered Azure resource catalog support (Tier 1 guided PaaS with security bundling + Tier 2 universal long-tail).
- Dynamic parsing and enforcement of Markdown Gold Standards in `common_standards/*.md`.
- Automated Enterprise Security Triad (deny public network access, private endpoint, and Hub Private DNS zone links) for all PaaS services.
- Repository topology traversal and AST/regex discovery of existing Subnets and Resource Groups.
- Scaffolding decoupled `data "azurerm_*"` blocks instead of hardcoded strings or remote state files.
- Automated subscription backend mapping for Azure Blob storage (`backend.tf`).
- Unified terminal diff preview with in-session conversational tweaking and interactive confirmation gate before disk writes.
- Existing directory remediation mode.

### 6.2 Out of Scope for MVP
- AST-level plan destruction analysis (analyzing `terraform plan` output for resource replacement risks). Deferred to v2.
- Automated batch drift remediation across legacy folders (opening automated refactoring PRs). Deferred to v2.
- Multi-cloud providers (AWS / GCP). Deferred to future major releases.
- Bi-directional Policy-as-Code compilation (compiling Markdown to OPA/Checkov rules). Deferred to v2.

## 7. Success Metrics

*Each metric cross-references the functional requirements it validates. Counter-metrics ensure optimization does not undermine safety.*

### 7.1 Primary Metrics
- **SM-1: Platform PR Review Latency**
  - **Definition:** Average time spent by Platform/DevOps engineers reviewing an infrastructure pull request.
  - **Target:** Drops from **~60 minutes to < 15 minutes** per PR.
  - **Validates:** FR-7, FR-9, FR-10, FR-13, FR-14.
- **SM-2: Private Network & Endpoint Compliance**
  - **Definition:** Percentage of newly scaffolded PaaS resources that comply with enterprise private networking policies (zero public endpoints, verified private endpoint, linked private DNS zone).
  - **Target:** **100% compliance** across all newly authored PaaS resources in production subscriptions.
  - **Validates:** FR-12, FR-13.
- **SM-3: First-Pass Review & CI Acceptance**
  - **Definition:** Percentage of `ttassistant`-generated resources that pass CI static analysis, linting, and platform review without requiring manual rework.
  - **Target:** **$\ge$90%** first-pass acceptance rate.
  - **Validates:** FR-3, FR-8, FR-9, FR-10, FR-14, FR-16.

### 7.2 Secondary Metrics
- **SM-4: Developer Onboarding Acceleration**
  - **Definition:** Time required for a newly onboarded engineer to scaffold and commit their first fully compliant Azure module.
  - **Target:** **>50% reduction** in time-to-first-compliant-module compared to historical averages.
  - **Validates:** FR-1, FR-2, FR-6.

### 7.3 Counter-Metrics (Do Not Optimize)
- **SM-C1: Never Sacrifice Verification for Velocity**
  - **Definition:** Speed of dialogue completion or reduced keystroke counts.
  - **Guardrail:** The CLI must **never** auto-skip candidate subnet selection, bypass naming validation, or eliminate the diff confirmation prompt to optimize for raw completion speed. Human confirmation and architectural correctness strictly override interaction brevity.

## 8. Cross-Cutting Non-Functional Requirements (NFRs)

### 8.1 Performance & Latency Budgets
- **NFR-1 (CLI Startup):** Cold startup time of the CLI inside the VSCode terminal must not exceed **1.5 seconds** until the initial interactive prompt is rendered.
- **NFR-2 (Repository Traversal):** Recursive repository scanning and subnet discovery must complete in under **3.0 seconds** for monorepos containing up to 10,000 files.
- **NFR-3 (Memory Footprint):** CLI process memory footprint must remain under **150 MB RSS** during active execution.

### 8.2 Security & Data Governance
- **NFR-4 (Zero Credential Storage):** The CLI must not request, process, log, or persist Azure credentials, service principal secrets, or Bitbucket personal access tokens.
- **NFR-5 (Air-Gapped Operation):** The CLI must operate entirely locally against repository files without transmitting repository code, metadata, or file paths to unauthorized third-party external services.

### 8.3 Reliability & Determinism
- **NFR-6 (Idempotent Scaffolding):** Running `ttassistant` repeatedly with identical inputs against a target directory must produce deterministic, byte-for-byte identical HCL output.
- **NFR-7 (Atomic Disk Writes):** File writing must be atomic; any failure during write operations must leave existing repository files uncorrupted and rollback partial writes.

- **Distribution Channel:** Packaged as an enterprise Python wheel and distributed via the organization's **internal Python repository** (e.g., private Artifactory, Azure Artifacts, or private PyPI).

  ```bash
  pip install --index-url https://artifacts.internal.company.com/api/pypi/pypi-local/simple/ ttassistant
  ```
  Or executed on demand via `pipx`.

### 9.2 Runtime Environment & Compatibility
- **Python Version:** Compatible with Python 3.10, 3.11, and 3.12.
- **Operating Systems:** Fully tested and supported on Linux (Ubuntu 20.04+, RHEL 8+, Debian 11+) and Windows (Windows 10/11, PowerShell 7+, Command Prompt).
- **Terminal Capabilities:** Supports 256-color ANSI terminals with fallback to plain monochrome text when running in non-TTY or dumb terminals.
